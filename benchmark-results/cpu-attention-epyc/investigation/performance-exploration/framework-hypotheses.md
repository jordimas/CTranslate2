# Framework approaches and hypotheses

Inspected on 2026-11-23. These are source-code comparisons, not performance or accuracy measurements of the other frameworks. Links to `main`/`master` may change. Our installed oneDNN is 3.1.1; newer APIs seen upstream are not assumed available here.

## What the sources actually do

| Framework | Relevant implementation | What we can learn |
|---|---|---|
| PyTorch CPU FlashAttention | [Kernel](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cpu/FlashAttentionKernel.cpp#L1106) chooses query tiles from sequence length and conditionally uses packed BF16/FP16 BRGEMM. [CPUBlas](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/CPUBlas.cpp#L1014) caches oneDNN microkernel plans by dimensions/types and checks ISA support. | Dispatch by workload and capabilities; amortize plan creation. The packed attention branch is not directly our FP32-activation case. |
| OpenVINO CPU oneDNN attention | [Preparation](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/nodes/scaled_attn.cpp#L299) caches explicit QK/PV BRGEMM plans. [Execution](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_cpu/src/nodes/scaled_attn.cpp#L412) manages per-worker scratch, packs keys per batch/KV head, and processes query blocks; value packing is conditional on reduced precision. | Explicit kernel and packing control can avoid repeated generic SGEMM setup. This does not establish parity with CT2's existing SGEMM results. |
| oneDNN Graph | [SDPA dispatch](https://github.com/uxlfoundation/oneDNN/blob/main/src/graph/backend/dnnl/kernels/sdp.hpp#L45) has multiple implementations. [Decomposition configuration](https://github.com/uxlfoundation/oneDNN/blob/main/src/graph/backend/dnnl/kernels/sdp_decomp_config.cpp#L90) gates per-head execution on available batch/head parallelism under OpenMP and creates full-sequence per-head matmuls. | Whole-head fusion is an established option, but selecting it should consider available parallel work. Its comments give performance reasons, not our int8-compatibility guarantee. |
| ONNX Runtime CPU attention | [AttentionCPUBase](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/contrib_ops/cpu/bert/attention_cpu_base.h#L274) submits float QK as batched MLAS GEMM to expose batch and row parallelism, then combines additive-mask/bias work with the softmax pass when needed. | Compare scheduling and memory-pass reduction separately. This path uses MLAS, so it is not evidence that oneDNN query blocking preserves CT2 outputs. |
| llama.cpp / ggml CPU | [Attention](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ops.cpp#L8512) uses explicitly packed tiles, its SIMD GEMM, FP32 output accumulators and online softmax state. [Eligibility](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ops.cpp#L8948) depends on dtype, query count and SIMD constraints. | Owning the microkernel gives control over arithmetic and packing. Its online-softmax arithmetic is not a drop-in way to reproduce CT2's regular attention. |

PyTorch also [documents](https://docs.pytorch.org/docs/2.15/notes/numerical_accuracy.html#batched-computations-or-slice-computations) that mathematically equivalent batched and sliced computations need not agree bit-for-bit. The examples above are architectural precedents; none is evidence that our exact int8 output requirement is automatically satisfied.

## Hypotheses, tests, and current status

| ID | Hypothesis | Test / acceptance criterion | Status |
|---|---|---|---|
| H1 | Aligned, uninitialized scratch can reduce whole-head overhead without changing arithmetic. Inspired by explicit scratch management in OpenVINO/oneDNN. | Replace value-initialized `vector<float>` scores with an uninitialized `StorageView`; compare exact output and alternate timings against the committed whole-head implementation. | Tested at op/encoder level. Small improvement only; see paired logs and encoder JSON. Allocation policy and alignment change together, so the improvement is not attributed solely to zeroing. Not adopted in production source. |
| H2 | A shape-specific query tile can keep the reference arithmetic while recovering cache locality. Inspired by shape/ISA dispatch in PyTorch and ggml. | Try 192/240 query rows for Whisper's 1500-query, 1500-key, depth-64 encoder. Require bitwise attention/encoder comparisons, full transcripts and repeated timing. Keep other shapes on the compatibility path. | Both preserve the tested real large-v3 encoder output in int8 and float32. 256 rows reproduces the original int8 divergence. 240 randomized bitwise comparisons pass, and the final first-window encoder tensors match bit-for-bit. All eight full-transcription outputs per compute type have identical text and segments. Tile240 reduces total time by 2.2% (int8) / 3.6% (float32); see [measurements](report.md). This is not a universal tile choice: the earlier broad shape sweep has counterexamples. |
| H3 | Separate full-shape planning from tiled execution: retain the chosen reduction/blocking strategy and pack keys once. OpenVINO creates its QK/PV plans using full query length, then executes internal row/tail kernels; PyTorch also caches explicit plans. | Prototype with a supported microkernel API; check FP32 accumulation/scale placement, quantized activations and end-to-end outputs. Measure packing and plan overhead separately. | Follow-up prototype implemented using matching 3.1.1 private SGEMM interfaces, retaining the existing arithmetic kernels rather than introducing BRGEMM. Full-shape QK planning, one key pack per head, and a preserved full-shape PV block/tail schedule pass 228 randomized exact stage/quantization comparisons and both real encoder checks. Encoder time falls 10.9% (int8) / 7.1% (float32) versus regular attention in the new run. Full transcription preserves all text/timestamps, with a 2.7% int8 total-time reduction; float32 is effectively flat (0.5% within variability). Public-API adoption remains unresolved. See [planned execution results](../planned-attention/report.md). |
| H4 | Reusing bounded scratch across layers can remove allocation/page costs while preserving whole-head arithmetic. | Model-owned or allocator-managed workspace with explicit lifetime/cache release; compare allocation counts, peak/resident memory, exact output and latency. | Not implemented. Blind thread-local caching could retain up to 64 MiB per worker after inference/model unload, so it is not being introduced as an incidental optimization. |
| H5 | Choosing batch/head parallelism versus GEMM-internal parallelism can help low-head-count workloads. Inspired by ONNX Runtime and oneDNN Graph. | Sweep head/batch/thread counts; compare exact outputs because changing GEMM threading can also change rounding. | Deferred. Whisper large-v3 has 20 heads on 8 cores, so insufficient head parallelism is not the most obvious bottleneck here. |
| H6 | Scale placement is part of numerical compatibility, not just softmax precision. | Isolate alpha folded into SGEMM versus explicit scaling of scores; distinguish power-of-two and non-power-of-two scales. | Source-backed hypothesis, not a validated fix. PyTorch/ggml attention scale scores explicitly; CT2 passes scale as GEMM alpha. oneDNN's copy path also handles alpha while copying operands. Changing the fused path alone may change baseline results further. |
| H7 | Attention speedups may be hidden by decoding costs in this audio workload. | Profile total encode time/call count versus the full 60-second transcription; use encoder-only measurements to distinguish a kernel win from an end-to-end win. | One unfused int8 profiling pass: 58.61 s total, 9.35 s encoding across three calls (15.95%), 49.26 s outside encoding. The first-window tile240 encoder is 14.1% faster in elapsed time, suggesting only about 2% total-time reduction if representative of all calls. That projection is an inference; full transcription is measured separately. |


**H8, preserve internal boundaries, not only the algorithm family:** the new single-thread control changes 459/192,000 PV output values under generic 256-query blocking even with identical probabilities. The adapter instead preserves the original 48-query blocks and 60-query tail and matches exactly. This supports investigating explicit kernel/block scheduling; merely forcing the same copy/no-copy strategy is insufficient as a general numerical contract. See the [stage evidence](../planned-attention/randomized.log).

### Why a backend-version/ISA check would matter for H2

The [oneDNN 3.1.1 GEMM driver](https://github.com/uxlfoundation/oneDNN/blob/v3.1.1/src/cpu/x64/gemm/gemm_driver.cpp) selects copy/no-copy strategies from dimensions, transposes, strides, ISA and threading. We downloaded and inspected that exact version (`/tmp/ct2-onednn-gemm-driver.cpp`); `nocopy_checker_avx2` and `set_thread_opts` make these dependencies explicit. This is a plausible explanation for the shape sensitivity, not a proof of bit identity for every input at a chosen tile size.

Any production use of H2 would need narrow eligibility, fallback for unvalidated backend/ISA combinations, and regression coverage. Arbitrarily changing all oneDNN blocks to 192 or 240 is rejected by the counterexamples already found. A new explicit microkernel would need its own numerical contract; higher-precision or online-softmax results can be more accurate mathematically while still producing different int8 activations.

## Scope of the experiments

The committed compatibility implementation remains unchanged. Experimental libraries are under `/tmp/ct2-attn-variants/` and are selected through `LD_LIBRARY_PATH`. The tile library has a diagnostic-only `CT2_DIAG_DNNL_BLOCK` override; this is not a production option. Input, CPU affinity, threads and compute types match the earlier EPYC checks. Local measurements do not benchmark the upstream frameworks.

## Follow-up latency hypotheses

- **H9, group calls while preserving boundaries:** implemented and exact across 228 randomized cases, but neither QK nor PV grouping nor the workspace sweep produced a meaningful encoder latency improvement. Rejected as the next latency gain.
- **H10, fewer CPU threads:** 6/4-thread real encoders differed from the 8-thread reference, so they were rejected under the strict compatibility criterion before full transcription timing. This does not establish a recognition-quality regression.
- **H11, persist decoder weight packing:** CT2 enables persistent packing for MKL, not oneDNN. Private oneDNN 3.1.1 packing produced microbenchmark gains but has query-extent-dependent metadata; a pack-for-one plan silently failed to compute all five output rows. The tested hybrid bounds packed calls to five queries and retains raw fallback weights. Full per-packed-GEMM int32 verification and encoder/transcript checks pass. Combined with planned attention it reduces total time 7.6% versus regular attention in the new run, with process peak RSS increasing from 3.23 to 6.17 GiB. The tradeoff and private dependency prevent treating this as a general production fix.
- **H12, pack only weights actually used by small-query decoding:** avoid redundant encoder/cross-KV packed copies to reduce memory/setup costs. Not implemented or measured. A broader supported-API design still needs a dependency and numerical-contract decision.

[Follow-up measurements and limitations](../latency-tuning/report.md).

## Memory-constrained follow-up

H12 is now implemented and extended: pack only useful decoder weights, remove persistent raw fallback copies, and process larger integer GEMMs in five-query blocks. A name-only loader snapshot also releases originals as replacements finish. Full per-packed-GEMM int32 verification, exact encoder comparison and all transcription/timestamp checks pass. On the new 60-second INT8 run, combined planned attention + compact packing reduces time 5.6%; peak RSS rises 4.9% and post-inference RSS 3.5%, replacing the rejected near-doubling. Compact is the opt-in adapter's new default; the high-memory hybrid is historical only. [Measurements and limitations](../memory-bounded-packing/report.md).

## Extended-validation lessons

- **Accumulation mode is part of compatibility:** private and public oneDNN INT8 GEMMs differed in 660 initial fractional-beta cases. The compact adapter now explicitly supports checked beta 0/1/-1 and rejects other modes without raw fallback. This does not invalidate the beta-0 Whisper comparisons.
- **Thread context belongs in the plan contract:** eight-thread packing followed by one-thread compute reproduced incomplete outputs. Fixed matching contexts are now enforced; dynamic teams are excluded from INT8 packing. CT2's replica-pool initialization already configures matching load/run counts.
- **Unloaded RSS is not equivalent to retained live model data:** ordinary and compact variants both retain allocator memory. Diagnostic cache release/heap trim removes it; four cleaned reload cycles show only 9.3 MiB growth. Ordinary untrimmed RSS plateauing is not established, and no cleanup behavior was added to production.

The guarded adapter passes the [extended operator/application checks](../extended-validation/report.md), including 27 application comparisons, concurrency and reloads. New single-pass times are not performance measurements.
